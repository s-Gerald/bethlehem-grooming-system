# Receptionist access and authentication verification

Verified on October 24, 2026, using the current local working tree.

## Implementation

- `User::isReceptionist()` recognizes both valid receptionist type/subrole pairs. Clinic permissions, grooming access, and grooming-catalog visibility use that shared policy. Stored roles, labels, staff types, and payment attribution remain distinct.
- Both receptionists use the existing clinic and grooming workflows and view both service catalogs. Clinical mutations, service management, reports, and revenue remain restricted by existing backend policies.
- Existing login, `/api/me`, and staff identity responses use the updated permission methods. The existing sidebar revision includes those permissions, so deployment changes invalidate outdated identities during session verification.
- Normal navigation retains existing identity reuse, request deduplication, and data caching. No additional polling, dependencies, environment settings, database migrations, or Sanctum architecture changes were introduced.
- All 48 API asset references across 37 raw HTML pages include the new authentication version. Existing preload/script URLs stay aligned.

## Authentication findings

The reported normal/incognito account replacement was **not reproduced** by the isolated-context simulations. Those contexts have separate localStorage, sessionStorage, identities, caches, and event channels, while sharing a simulated token server. Backend tests separately exercise real Sanctum token issuance, authentication, revocation, locking, and expiry with fake email delivery.

Tests did establish four defects within a shared browser context:

1. A delayed password-sign-in response could clear a replacement login and install an older pending challenge.
2. A delayed OTP confirmation could overwrite a replacement login.
3. Logout waiting for server revocation could erase a replacement login after the old token was revoked.
4. A sibling tab's completed account switch cleared identity caches but retained the former account's document/workspace.

Regression tests failed before each fix. Login responses now check their original session generation/token and pending challenge before changing authentication state. Revocation completion checks token ownership before clearing storage. A protected document displaying a replaced staff token refreshes once, using the existing identity-change refresh pattern.

These findings do not establish the cause of the reported switch between genuinely isolated normal/incognito contexts.
