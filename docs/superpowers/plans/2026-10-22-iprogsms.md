# iProgSMS implementation plan

Goal: replace the existing phone preview with authenticated, provider-verified SMS and optional pre-registration enforcement.

Architecture: a focused provider service handles JSON requests and sanitizes results. A persistent attempt per customer binds destination, generation, account snapshot, expiry and attempt budget. Shared cache operation locks serialize customer/destination operations without holding database locks over HTTP; short database transactions finalize changes. A keyed code fingerprint binds the provider code to its generation without storing plaintext or replacing provider verification.

Constraints: current gerald-frontend branch; no commits, branches, deployment, live SMS or changes to .env. Both feature flags default false. Existing email OTP, booking eligibility, readonly Settings and caching remain.

1. Add HTTP-faked feature tests in tests/Feature/PhoneVerificationTest.php; run and confirm missing routes fail. Implement IprogSmsOtpService, CustomerPhoneVerificationService, PhoneVerificationController, one forward attempt migration, services config and example placeholders. Verify malformed responses, ownership, duplicate phones, cooldown, expiry, five attempts across resends, generation races, replay, changed account, and provider-success/database-failure recovery.
2. Extend existing authenticated routes with customer-only send/verify/resend and a shared enforcement middleware on both submission routes. Recheck enforcement on the already locked customer within both submission transactions. Test all flag combinations and staff isolation; preserve ongoing registration checks.
3. Update the existing phone modal, pre-registration button handler, API cache invalidation and Settings profile refresh. Expose server flags through /me and existing access response. Remove preview markup/styles and update the existing frontend regression in place. Verify missing/editable phones, backend-confirmed send, shared six-cell paste, loading, cooldown, errors, dismissal, focus and server-confirmed navigation using the Node harness.
4. Replace docs/customer-phone-verification.md with configuration, lifecycle, operational recovery and deployment instructions. Run affected PHP suites and frontend regressions. Inspect the existing browser UI without submitting forms or manually exercising navigation.

Review focus: late responses after cancellation; stale generations after resend; destination conflicts introduced during HTTP; local commit failure after provider acceptance; fail-closed enforced/unavailable configuration. Real multiprocess MySQL concurrency and live provider lifecycle must be reported separately if unavailable.
